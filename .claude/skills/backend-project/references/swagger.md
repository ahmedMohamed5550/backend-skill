# Swagger Documentation

- Use `darkaonline/l5-swagger` for API documentation.
- Use traditional PHPDoc Swagger annotations (`@OA`), not PHP Attributes.
- Every API endpoint must have Swagger documentation.
- Document the HTTP method, URL, summary, parameters, request body, and responses.
- Document request fields and their validation requirements.
- Document Bearer Token authentication for protected endpoints.
- Document successful and error response structures according to the project's API response standard.
- Ensure all Swagger annotations are valid and documentation can be generated without errors.
- Swagger UI must allow testing endpoints using the "Try it out" feature.

## Route and Permission Documentation

- Every API endpoint must have its exact generated route documented in its Swagger annotation.
- Every API endpoint must document the exact permission assigned to its Controller action.
- The documented permission must be identical to the permission registered in the Controller constructor middleware and Spatie permission seeders.
- Never invent, rename, or reconstruct permission names inside Swagger annotations.
- Swagger documentation must use the exact route path, HTTP method, and permission generated by the backend implementation.
- Document the required permission using this exact OpenAPI annotation format:

  `x={"required-permission": "products-list"},`

- For public endpoints that do not require permissions, use:

  `x={"required-permission": null},`

- Additionally, include the permission visibly in the endpoint's `description` using this exact format:

  `description="Endpoint description.<br><br>🔒 <b>Required permission:</b> <code>products-list</code>",`

- For public endpoints, use:

  `description="Endpoint description.<br><br>🌐 <b>Public endpoint</b>",`

- Every endpoint must have its own permission documentation, even when multiple endpoints share the same permission.
- Ensure the documented permission matches the actual authorization middleware applied to the endpoint.
- Keep Swagger documentation synchronized whenever routes, Controller actions, or permissions change.
- The generated OpenAPI specification is the official API contract for Frontend and Mobile integration.
- Frontend and Mobile developers must consume the documented route paths, HTTP methods, request schemas, response schemas, and permission names without independently inventing or modifying them.

## Permission Visibility in Swagger UI

- Every endpoint's required permission must be clearly visible in Swagger UI through its description.
- Display the permission using the label `Required permission` and the exact permission name inside an HTML `<code>` element.
- Read the permission value from the same value used in the `x={"required-permission": ...}` annotation.
- For endpoints with `x={"required-permission": null}`, clearly display `Public endpoint`.
- Do not rely on Swagger UI customization to display the permission; include it directly in the endpoint description as specified above.
- Do not change the existing permission naming, generation, registration, or authorization logic to achieve this.
- Do not create a separate source of permission values for the UI.
- Ensure the permission displayed in the description always matches the OpenAPI extension, Controller middleware, and Spatie permission seeders.

## Approved Annotation Example

Place the global annotations (`@OA\Info`, `@OA\Server`, `@OA\SecurityScheme` for `bearerAuth`) on the Auth Controller class docblock so they are generated once.

Protected endpoint example (`ProductsController::store`):

```php
/**
 * Create a product.
 *
 * @OA\Post(
 *     path="/api/v1/products",
 *     operationId="productsStore",
 *     tags={"Products"},
 *     summary="Create a product",
 *     description="Create a new product.<br><br>🔒 <b>Required permission:</b> <code>products-create</code>",
 *     security={{"bearerAuth": {}}},
 *     x={"required-permission": "products-create"},
 *
 *     @OA\RequestBody(
 *         required=true,
 *
 *         @OA\JsonContent(
 *             required={"name", "price", "stock_quantity"},
 *
 *             @OA\Property(property="name", type="string", example="Espresso"),
 *             @OA\Property(property="description", type="string", nullable=true, example="Double shot espresso"),
 *             @OA\Property(property="price", type="number", format="float", example=3.50),
 *             @OA\Property(property="stock_quantity", type="integer", example=100)
 *         )
 *     ),
 *
 *     @OA\Response(response=201, description="Products created successfully"),
 *     @OA\Response(response=401, description="Unauthenticated"),
 *     @OA\Response(response=403, description="Missing products-create permission"),
 *     @OA\Response(response=422, description="Validation failed"),
 *     @OA\Response(response=500, description="Server error")
 * )
 */
public function store(StoreProductRequest $request): JsonResponse
```

Public endpoint example (login):

```php
/**
 * @OA\Post(
 *     path="/api/v1/auth/login",
 *     operationId="authLogin",
 *     tags={"Auth"},
 *     summary="Login",
 *     description="Authenticate a user and return a Bearer token.<br><br>🌐 <b>Public endpoint</b>",
 *     x={"required-permission": null},
 *
 *     @OA\RequestBody(
 *         required=true,
 *
 *         @OA\JsonContent(
 *             required={"email", "password"},
 *
 *             @OA\Property(property="email", type="string", format="email", example="admin@example.local"),
 *             @OA\Property(property="password", type="string", format="password", example="password")
 *         )
 *     ),
 *
 *     @OA\Response(response=200, description="Logged in successfully"),
 *     @OA\Response(response=401, description="Invalid credentials"),
 *     @OA\Response(response=422, description="Validation failed")
 * )
 */
```

Follow the same structure for every endpoint: exact route path, `operationId`, `tags`, `summary`, permission `description` and `x` extension, `security` for protected endpoints, request body or parameters, and every applicable response code.
