# Authentication Standards

## Default API Authentication
- Laravel Passport is the approved default API authentication system.
- Passport must be included in the base project dependencies.
- Prepare the project to use Passport for API authentication.
- Do not replace Passport with Sanctum or another authentication system.
- Keep roles and permissions on the `api` guard: set `auth.defaults.guard` to `api`, define the Passport `api` driver guard in `config/auth.php`, and create all Spatie roles and permissions with `guard_name` `api` (the seeder should read the guard from `config('auth.defaults.guard')`).
- The scaffold applies this configuration automatically: it installs the approved `templates/config/auth.php` over the Laravel skeleton file (default guard `api`; `api` guard with the `passport` driver on the `users` provider). Do not restore the skeleton's session-only configuration or the `web` default guard.

## Authentication Features
Authentication features must be implemented according to the project's business requirements.

Do not assume that every optional authentication feature is required.

## Token Lifecycle
Every project implements the full Access Token and Refresh Token lifecycle on Passport's own OAuth 2.0 machinery. The scaffold installs the complete Auth module (routes, `AuthController`, `AuthService`, `LoginRequest`, `RegisterRequest`, `ForgotPasswordRequest`, `ResetPasswordRequest`, and the `AuthTest`, `RegisterTest`, `PasswordResetTest`, `EmailVerificationTest` feature specs) plus `config/oauth.php` and the `AppServiceProvider` TTL registration and route hardening, so the lifecycle works in every newly generated project without hand-written token code.

### Approved flow: authorization code + PKCE with the public first-party client

Login is a two-step flow. All requests and responses are JSON; no browser, session, or consent screen is involved.

1. **`POST /api/v1/auth/login`** (public) — verifies the email/password credentials, then drives Passport's authorization server directly: it builds the authorization request for the first-party client and approves it as the authenticated user, and returns the short-lived **authorization code** in the approved envelope: `data.code`.
2. **`POST /oauth/token`** (`grant_type=authorization_code`) — the client exchanges the code plus its PKCE `code_verifier` for the **access token + refresh token** pair: `{token_type: "Bearer", expires_in, access_token, refresh_token}`. Every field of the parameter list below is required: omitting `client_id`, `redirect_uri`, `code`, or `code_verifier` answers `400 invalid_request` with a `hint` naming the missing parameter, and a `redirect_uri` that differs from the login value answers `400 invalid_request` (`Invalid redirect URI`). The endpoint is Passport's `AccessTokenController`, registered by the application itself (see Passport route hardening below).
3. **`POST /oauth/token`** (`grant_type=refresh_token`) — the client presents the refresh token plus the `client_id` and receives a **new pair**. Passport's refresh token grant rotates: it revokes the submitted refresh token and its access token and issues fresh ones, so a consumed refresh token can never be reused.
4. **`POST /api/v1/auth/logout`** (`auth:api`) — revokes the current access token **and** its associated refresh token (`oauth_refresh_tokens.access_token_id`). The token immediately stops authenticating.
5. **`GET /api/v1/auth/me`** (`auth:api`) — returns the authenticated user's profile.

The PKCE pair (RFC 7636) is generated by the client: `code_verifier` is a random 43-128 character unreserved string; `code_challenge` is `base64url(sha256(code_verifier))`. The login request carries `client_id`, `redirect_uri`, `code_challenge`, and `code_challenge_method=S256`; the token exchange carries `client_id`, `redirect_uri`, `code`, and `code_verifier`. S256 is the only accepted method — the `LoginRequest` template rejects `plain` so the PKCE downgrade path stays closed.

**Public client configuration discovery.** The generated `docs/API_DOCUMENTATION.md` starts with the mandatory **Public Authentication Configuration** section (references/api-documentation.md, 4.1): the `client_id` and the first registered `redirect_uri` of the seeded First Party PKCE Client, resolved from the database when the documentation is generated, plus `code_challenge_method: S256`. The public documentation endpoint (`GET /api/v1/documentation`) serves the file beginning with that section and rebuilds it from the database at request time, so a re-seeded database needs no documentation regeneration and frontends read the runtime configuration directly from the documentation response instead of hardcoding client ids. Web and Mobile clients use the same client and redirect URI. The section exposes only these public values — never a client secret or any other internal credential (the first-party client is public and has none). When the client row is missing (seeding has not run), the endpoint serves the documentation without the section and logs a warning; it must not fail. The endpoint spec is the scaffold-installed `tests/Feature/V1/DocumentationTest.php` (see `references/testing.md`).

### Hard requirements

- Do not manually implement token generation or storage: no manual JWT encoding, no manual refresh token rows, no custom encryption. Every token is issued, persisted, rotated, and revoked by Passport and league/oauth2-server through the authorization server.
- Do not use the password grant or the implicit grant. Both are deprecated/disabled in Passport 13; the seeded client declares only `authorization_code` and `refresh_token`.
- Never expose confidential client secrets to public frontends. The first-party client is **public** (`secret = null`): frontends hold only its id, and PKCE protects the exchange instead of a secret. Never seed a secret into the first-party client and never ship a secret in frontend code or responses.
- Do not issue login tokens with `User::createToken()`; personal access tokens carry no refresh token and bypass the lifecycle. The personal access client remains seeded only so `createToken()` keeps working for non-lifecycle internal uses (e.g. Mail flows that need it).
- Do not drive the login through `GET /oauth/authorize` or the web session guard: the skill's backend is API-only and the authorize endpoint does not exist in a generated project (see Passport route hardening below). The JSON login endpoint performs the same authorization server interaction server-side, as implemented in the approved `AuthService` template.
- Do not modify the approved `AuthService` token mechanics to "simplify" the flow: removing PKCE fields, hardcoding the client id, or catching the `OAuthServerException` as a 500 are all violations.

### Passport route hardening

`POST /oauth/token` is the only OAuth endpoint a generated project exposes:

- `AppServiceProvider::register()` calls `Passport::ignoreRoutes()`. The call must run in `register()` — every provider's `register()` completes before any `boot()`, so the flag is already set when `PassportServiceProvider` decides whether to register its routes.
- `AppServiceProvider::boot()` registers the endpoint itself through Passport's own `AccessTokenController`, with the `throttle` middleware (Passport's rate limiting on the token endpoint) and the `passport.token` route name, outside the `api/v1` prefix. No extra PSR-7 setup is required: the framework binds `ServerRequestInterface` globally, which is what `issueToken()` resolves.
- Everything else Passport would register — the browser `GET`/`POST`/`DELETE /oauth/authorize` authorize/consent flow (which would accept league's default **plain** PKCE verifier and would need a session login), `POST /oauth/token/refresh`, the personal-token and scope endpoints, and the device grant routes — stays disabled and answers `404`.

Do not re-enable Passport's automatic routes, do not register any additional OAuth route, and do not move `/oauth/token` into the `api/v1` prefix. `tests/Feature/V1/AuthTest.php` asserts the whole route table contract.

### Rate limiting on the auth endpoints

- The login and register endpoints run under the `throttle:auth` limiter: 5 attempts per minute and 30 per hour, enforced independently per normalized email and per IP. Exceeding any limit answers the approved 429 envelope with the `Retry-After` header (see `references/api-standards.md`, Rate Limiting).
- The `POST /oauth/token` registration keeps Passport's own `throttle` middleware (60 requests per minute per IP) — the same middleware Passport itself registers; do not remove or replace it.
- Every `/api/v1` route additionally carries the `api` baseline limiter (`60` requests per minute per user id or IP) enabled through `$middleware->throttleApi()` in the approved `bootstrap/app.php` template.
- The password reset endpoints (`forgot-password`, `reset-password`) run under the `throttle:password_reset` limiter: 5 attempts per minute and 30 per hour, enforced independently per normalized email and per IP (the same bucket pattern as `auth`).
- The resend verification endpoint runs under the `throttle:email_resend` limiter: 6 requests per minute and 30 per hour, keyed per authenticated user id (falling back to IP before authentication resolves).
- Reserved, inert config keys for the future OTP limiters live in `config/rate_limiting.php` (`otp_send_*`, `otp_verify_*`); they attach to routes only when that optional feature is implemented and approved.

### Response conventions

- The Auth module endpoints (`register`, `login`, `logout`, `me`, `forgot-password`, `reset-password`, `email/verify/{uuid}/{hash}`, `email/resend`) use the approved `apiResponse()` envelope.
- Passport's `/oauth/token` endpoint is **not** wrapped in the envelope: its success and error payloads follow the OAuth 2.0 wire format — success `{token_type, expires_in, access_token, refresh_token}` and errors `{error, error_description, hint?}` with HTTP 400 (`invalid_grant`, `invalid_request`) or 401 (`invalid_client`). This is the approved exception to the single-envelope rule; do not intercept or transform `/oauth/token` responses to force the envelope shape.
- Failed credential verification and an invalid `client_id`/`redirect_uri` at `login` both return the approved 422 envelope (the `AuthService` template converts league's `OAuthServerException` for the expected client failures).
- `register` answers **201** with the `Account registered successfully. A verification email has been sent to your email address.` message and the new user's public profile (`uuid`, `name`, `email`, `email_verified_at: null`); validation failures — including the duplicate-email `unique` rule — answer the standard 422 envelope. Registration answers 422 for an existing address; unlike the password reset flow, it never hides whether an account exists (registration requires a unique address by definition).
- `forgot-password` always answers the identical neutral 200 (its message is the same for registered and unknown addresses); the native broker throttle surfaces as 429 with `Retry-After`; a consumed/invalid reset token answers 422 with the `This password reset token is invalid or has expired.` message.
- The verification route answers 200 with the `The email address has been verified successfully.` message (idempotent for already verified accounts), 403 for expired/tampered signatures (the `This verification link is invalid or has expired.` message, rendered by the central `InvalidSignatureException` handler in `bootstrap/app.php`), 404 for an unknown uuid, and 422 for a signature-valid link whose hash does not match the addressed user's email. `email/resend` answers 200 with the `Verification email sent successfully.` message, and 422 with the `The email address is already verified.` message when the account is already verified.

### Token lifetimes

- `templates/config/oauth.php` defines `access_token_expires_in` (minutes, default 15) and `refresh_token_expires_in` (days, default 30), overridable through `OAUTH_ACCESS_TOKEN_EXPIRES_IN` / `OAUTH_REFRESH_TOKEN_EXPIRES_IN`.
- The approved `AppServiceProvider` template registers them in `boot()` via `Passport::tokensExpireIn()` and `Passport::refreshTokensExpireIn()`. Never set TTLs elsewhere; Passport reads them when the authorization server resolves.
- Refresh token rotation and old-token invalidation are Passport defaults (`Passport::$revokeRefreshTokenAfterUse = true`); do not disable them.

## Password Reset

Every project ships the Forgot Password and Reset Password endpoints as part of the default Auth module, implemented **only** through Laravel's native Password broker — no custom token tables, hashes, or expiries.

### Approved flow

1. **`POST /api/v1/auth/forgot-password`** (public, `throttle:password_reset`) — `ForgotPasswordRequest` validates the email, then the `AuthService` calls `Password::sendResetLink()`. The broker stores a hashed, expiring token (60 minutes, `auth.passwords.users.expire`) in `password_reset_tokens` and mails the native `ResetPassword` notification. The endpoint answers the **same neutral 200** whether or not the address is registered (`Password::RESET_LINK_SENT` and `Password::INVALID_USER` both succeed) so it can never be used to enumerate accounts.
2. The emailed link points at the frontend reset-password page with `token` and `email` in the query. The `AppServiceProvider` template builds it through `ResetPassword::createUrlUsing()` from `config('app.frontend_url')` (`FRONTEND_URL`, defaulting to the API URL until a separate frontend exists) — the native notification would otherwise look up a `password.reset` web route that does not exist in this API-only project. Do not remove the `createUrlUsing` registration and do not register a `password.reset` route instead.
3. **`POST /api/v1/auth/reset-password`** (public, `throttle:password_reset`) — `ResetPasswordRequest` validates `token`, `email`, `password` (min 8, confirmed through `password_confirmation`), then the `AuthService` calls `Password::reset()`. The broker validates the hashed token, resolves the user, and deletes the token row; the closure updates the password inside `DB::transaction()` (the model's `hashed` cast hashes it), rotates `remember_token`, and dispatches the native `PasswordReset` event. Invalid or expired tokens answer the approved 422 envelope, never a 500.

Hard requirements:

- Do not reimplement token generation, hashing, expiry, or single-use semantics: the broker owns them. The reset token is single-use — the broker deletes the row on success, so replaying a consumed token answers 422.
- Do not create custom reset controllers, tables, or notifications. The Auth module keeps exactly one Controller and one Service; the reset actions live in `AuthController`/`AuthService` next to login/logout/me.
- The native broker throttle (`auth.passwords.users.throttle`, 60 seconds per email) rejects a second link for the same address: the `AuthService` reports it as 429 (with `Retry-After: <throttle seconds>`) through `TooManyRequestsHttpException`, rendered by the central exception handler.
- Keep the neutral-answer rule for unknown addresses; returning 422/404 for unknown emails is a violation (account enumeration).

## Registration

Every project ships the Register endpoint as part of the default Auth module. It validates the input, creates the user, and automatically sends the framework's verification email through the native `MustVerifyEmail` machinery — no custom notification, no manual mail, no tokens.

### Approved flow

1. **`POST /api/v1/auth/register`** (public, `throttle:auth`) — `RegisterRequest` validates `name`, `email` (`required`, `email`, `max:255`, `unique:users`), and `password` (`min:8`, `confirmed` through `password_confirmation`; the same shape `ResetPasswordRequest` accepts). `AuthService::register()` creates the user inside `DB::transaction()` — the model's `hashed` cast hashes the plain password and the `creating` hook generates the uuid — and then calls the native `$user->sendEmailVerificationNotification()` **after the transaction commits** (the `VerifyEmail` notification is queued, so it must never fire for an uncommitted row). The endpoint answers **201** with the new user's public profile (`uuid`, `name`, `email`, `email_verified_at: null`) and the `Account registered successfully. A verification email has been sent to your email address.` message.
2. The verification email is the framework's native `VerifyEmail` notification carrying the signed link of the Email Verification flow below — registration is the flow's first and automatic sender.
3. Registration does **not** authenticate the caller and issues no tokens: clients log in afterwards through the unchanged login + PKCE flow (Token Lifecycle above). Email verification does not gate login.

Hard requirements:

- Keep the automatic verification email: registration must send the native notification itself, never leave the client to call `email/resend` to receive the first link.
- Do not issue tokens, assign roles, or add profile mutations at registration beyond what the project's business requirements explicitly ask for.
- Do not move the password rules out of `RegisterRequest` or accept an unconfirmed password; the unique rule must stay on `email` so duplicate addresses answer the standard 422 validation envelope.
- The response exposes the new user's public fields only (`uuid`, `name`, `email`, `email_verified_at`) — never the database `id`, the hashed password, or the remember token.

## Email Verification

Every project ships Email Verification and Resend Verification Email as part of the default Auth module, implemented **only** through Laravel's native `MustVerifyEmail` machinery — the framework's `VerifyEmail` notification, its signed URL, and its `markEmailAsVerified()`.

- The approved `User` model template implements `Illuminate\Contracts\Auth\MustVerifyEmail` (the base `Illuminate\Foundation\Auth\User` already carries the `MustVerifyEmail` and `CanResetPassword` traits). Do not remove the contract.
- `users.email_verified_at` comes from the framework's default users migration; no extra migration is required.

### Approved flow

1. **`GET /api/v1/auth/email/verify/{uuid}/{hash}`** — the handler the framework's `VerifyEmail` notification builds its signed URL for. The route is registered in `routes/v1/auth.php` with the native route name **`verification.verify`** and Laravel's `signed` middleware (`ValidateSignature`), and it is public: the signature **is** the authorization, exactly like Laravel's own verification flow, because an email client cannot present a Bearer token. The link addresses the user by **uuid** — public API identifiers are UUIDs, never database ids — so the approved `AppServiceProvider` template registers `VerifyEmail::createUrlUsing()` (Laravel's official URL customization hook, the same mechanism as the `ResetPassword::createUrlUsing()` registration of the Password Reset flow): it builds the same `URL::temporarySignedRoute('verification.verify', ...)` URL with the `uuid` route parameter instead of the framework default's database `id`, while everything else stays native — the same notification, the 60-minute expiry from `auth.verification.expire`, and the `sha1(email)` hash. Do not remove that registration: without it, `URL::temporarySignedRoute()` throws a `MissingRouteParameterException` against the `{uuid}` route the moment a notification is mailed. The `signed` middleware rejects an expired link (60 minutes) or a tampered one with 403; the central exception handler renders it as the approved envelope with the `This verification link is invalid or has expired.` message. The `AuthService::verifyEmail()` resolves the user by uuid (`User::where('uuid', $uuid)->firstOrFail()`), then checks `hash_equals(sha1($user->getEmailForVerification()), $hash)` (mirroring the framework's own `EmailVerificationRequest` validation), and calls `markEmailAsVerified()` inside `DB::transaction()` — stamping `email_verified_at` and dispatching the native `Verified` event. Following the link again stays idempotently successful.
2. **`POST /api/v1/auth/email/resend`** (`auth:api`, `throttle:email_resend`) — calls the native `$user->sendEmailVerificationNotification()`, which mails the framework's `VerifyEmail` notification untouched (the route named `verification.verify` is exactly the name the notification builds its `URL::temporarySignedRoute` URL for — through the `createUrlUsing()` hook — so no custom notification is needed). Resending for an already verified account is a 422 business failure, not a silent success.
3. **`GET /api/v1/auth/me`** includes `email_verified_at` (null until verified) so clients know the verification status.

Hard requirements:

- Do not build custom verification tokens, tables, or notifications; do not rename the `verification.verify` route (the framework's notification hardcodes it); do not move the signed route behind `auth:api` (it would break every emailed link) and do not remove the `signed` middleware (it is the only protection the route has).
- Keep `{uuid}` as the link's user parameter everywhere — Route, Controller, Service — and never rebuild the verification URL with the database `id`: public API identifiers are UUIDs. Do not remove the `VerifyEmail::createUrlUsing()` registration in the approved `AppServiceProvider` template.
- Route names for `verification.verify` must stay **unique**, and **`laravel/fortify` must not be installed in a generated project**: Fortify is not part of the approved architecture — Laravel's native machinery plus Passport own every auth flow (see Hard requirements above). Fortify ships with `Features::emailVerification()` enabled in its vendor default config and registers a session-authenticated `/email/verify/{id}/{hash}` web route under that exact name; because `URL::temporarySignedRoute()` resolves the name to the route registered last, the emailed links would then point at Fortify's route and answer `401`. The scaffold and the Completion Gate therefore verify Fortify stays absent (`composer.json` carries no `laravel/fortify`, no `config/fortify.php` exists). Never reintroduce Fortify or any other package or route that registers `verification.verify` without explicit user approval and a confirmed absence of route-name conflicts.
- Never trust the `{hash}` without comparing it to `sha1(email)` of the addressed user, and never mark an email verified through any other endpoint.
- When a project gains a web frontend, the verification link MAY be redirected there by overriding the notification's URL — but the base foundation keeps the native signed route as the link target so the flow works without a frontend.

## Social Login (Socialite)

Social login is an optional feature implemented with Laravel Socialite as the provider identity resolver. The feature has a two-level opt-in:

- **Installing Socialite does not activate Social Login.** Adding the package only makes the capability available; the Auth module, routes, and the default Email/Password + Passport flow must stay completely unchanged.
- Install the package only when the project requirements request social login support, and implement the Social Login feature only when the requirements explicitly request it — and only for the requested providers.
- Socialite is not a base dependency: never add it to the base scaffold or `templates/composer.json` (see `references/dependencies.md`, Optional Dependencies).

### Providers

- Prefer the Socialite built-in drivers (Google, GitHub, Facebook, LinkedIn, X, GitLab, Bitbucket) for the requested providers.
- When a requested provider has no built-in driver (for example Sign in with Apple), use the approved community driver manager `socialiteproviders/manager` with its provider package. Do not hand-roll a custom OAuth client.
- Enable only the requested providers through an explicit allowlist: the `{provider}` route parameter is validated against it and every other provider answers 404/422. Never enable a provider the project did not request.
- Keep provider credentials in environment variables through Socialite's standard `config/services.php` convention; never hardcode credentials in application source code.

### Approved flow: identity resolution only, then the existing token lifecycle

Socialite verifies the provider identity and does nothing else. Token issuance is the existing authorization code + PKCE flow of the seeded public first-party client — exactly the `AuthService::login()` mechanics:

1. **`POST /api/v1/auth/social/{provider}`** (public) — the client presents the provider token it obtained from the provider (native SDK on mobile, provider JS SDK on web) plus the same client/PKCE fields as `login` (`client_id`, `redirect_uri`, `code_challenge`, `code_challenge_method=S256`). The backend verifies the provider token, resolves or creates the user, drives the authorization server through the same `issueAuthorizationCode()` mechanics, and returns the short-lived authorization code as `data.code` in the approved envelope.
2. **`POST /oauth/token`** (`grant_type=authorization_code`) — unchanged: the code plus the `code_verifier` are exchanged for the access token + refresh token pair, with the same required `client_id` and `redirect_uri` fields as the password login (see Token Lifecycle above).
3. Refresh rotation, logout revocation, and the `/oauth/token` response conventions are identical to the password login (see Token Lifecycle above).

Hard requirements:

- Do not generate, store, or transform tokens for social login outside this flow: no `User::createToken()`, no manual JWT encoding, no custom grant. The same `issueAuthorizationCode()` mechanics inside `AuthService` remain the single token issuance path for every login method.
- The social login response contract is identical to the login response (`data.code`), and the social login endpoint runs under the same `throttle:auth` limiter.
- Handle the social login failure messages directly in the implementation as English literals (the snippets below show the exact texts). When the project explicitly requested additional languages, also add the same keys to the generated `lang/en/messages.php` and `lang/{locale}/messages.php` files and convert the literals to `__('messages.*')` calls (references/localization.md, Adding Additional Languages), and document the endpoints in Swagger and `docs/API_DOCUMENTATION.md` like any other Auth endpoint.

### Provider tokens: access tokens and ID tokens

Support both token types, verifying each with the correct method — never verify one as the other:

- **Access token** — resolve the identity through the provider driver: `Socialite::driver($provider)->userFromToken($token)`. The provider validates the token when the identity endpoint is fetched.
- **ID token** (what native mobile SDKs commonly return, e.g. Google Sign-In) — verify the JWT before trusting its claims: signature against the provider's published public keys (JWKS), plus issuer, audience (the project's provider client id), and expiry. Use an approved dependency for the verification (`firebase/php-jwt`, or `google/apiclient` for Google ID tokens); never accept an unverified decoded payload.

Do not request provider scopes beyond what identity resolution requires unless the business requirements explicitly ask for provider API access.

### Account resolution and linking

- Match an existing social identity on `(provider, provider_user_id)` only — never on email alone.
- Auto-link by email only when the provider confirms the email is verified. When the email matches an existing user without that confirmation, reject the request with the approved 422 envelope and direct the user to log in with the password and link the account explicitly.
- Create new provider users inside `DB::transaction()` together with their `social_accounts` row, assign the project's defined default role, and set `email_verified_at` only when the provider confirms the email.
- `POST /api/v1/auth/social/{provider}/link` (`auth:api`) links the authenticated user to a provider identity; `DELETE /api/v1/auth/social/{provider}` (`auth:api`) unlinks. Reject unlink when it would leave the account without a password and without any remaining provider identity.
- Make `users.password` nullable only in projects that implement Social Login and require social-only accounts; never change the users table migration in projects without the feature.

### Social accounts table

When Social Login is implemented, create `social_accounts` following the database standards (auto-incrementing `id`, unique `uuid`, `$table->timestamps()`, FK with `ON DELETE CASCADE`):

- `user_id` — FK to `users.id`.
- `provider` — string(255), the allowlisted provider name.
- `provider_user_id` — string(255), the provider's stable user identifier.
- Unique composite index on (`provider`, `provider_user_id`).

### Provider token storage

- Do not store provider access or refresh tokens by default; discard them after identity resolution.
- Store them only when the business requirements explicitly require provider API access, and always encrypted at rest (Laravel encrypted casts / `Crypt`). Never store provider tokens in plain text.

### Web redirect/callback flow

- Deferred by default: do not implement Socialite's server-side redirect/callback flow unless the project requirements explicitly request it.
- When approved, register `GET /api/v1/auth/social/{provider}/redirect` and `GET /api/v1/auth/social/{provider}/callback` with `stateless()` (the API has no sessions) and document that `stateless()` skips OAuth state validation; token issuance still goes through the same authorization code + PKCE flow.

### Testing social login

- Follow `references/testing.md`: never call real providers; fake the driver (mock `Socialite::driver()` or `Http::fake()` the provider endpoints) and test with controlled provider identities.
- Cover: identity resolution, verified and unverified email auto-link behavior, collision rejection, link/unlink rules, unrequested-provider rejection, and the full code → exchange → refresh → logout path through the unchanged `/oauth/token` machinery.

### Integration steps and templates (run only when the feature is requested)

The scaffold never installs or copies anything Social Login related, and `templates/composer.json` never gains Socialite. Perform these steps in order only when the project requirements explicitly request the feature, for the requested providers:

1. Install the approved packages: `composer require "laravel/socialite:^5.33"`. When a requested provider has no built-in driver, also `composer require "socialiteproviders/manager:^4.10"` plus the provider package pinned to its latest stable version (for example `socialiteproviders/apple:^6.1` for Sign in with Apple). Verify the versions against PHP `^8.4` / Laravel `^13.0` before installing.
2. Copy the optional templates, inspecting every target file first and never silently overwriting an existing file (see SKILL.md, Mandatory Templates):
   - `templates/config/social.php` → `config/social.php`
   - `templates/database/migrations/2024_01_01_000001_create_social_accounts_table.php` → `database/migrations/`, renamed with the current timestamp
   - `templates/app/Models/V1/SocialAccount.php` → `app/Models/V1/SocialAccount.php`
   - `templates/app/Http/Requests/V1/Auth/SocialLoginRequest.php` → `app/Http/Requests/V1/Auth/SocialLoginRequest.php`
   - `templates/app/Http/Requests/V1/Auth/LinkProviderRequest.php` → `app/Http/Requests/V1/Auth/LinkProviderRequest.php`
   - `templates/tests/Feature/V1/SocialLoginTest.php` → `tests/Feature/V1/SocialLoginTest.php` (adapted in step 10)
3. Make `users.password` nullable in the framework's default users migration — the same migration that carries the `uuid` column — only in projects implementing Social Login.
4. Configure `.env`: `SOCIAL_ENABLED_PROVIDERS` (requested providers only), `SOCIAL_DEFAULT_ROLE` (the project's defined default role), and the provider credentials through Socialite's standard `SERVICES_*` variables (for example `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`).
5. Merge the social routes into the existing `routes/v1/auth.php` — never create a second Auth route file. `socialLogin` is public like `login`; `linkProvider` and `unlinkProvider` join the existing `auth:api` group:

        Route::post('/social/{provider}', 'socialLogin')->middleware('throttle:auth'); // public, like login

        Route::middleware('auth:api')->group(function () {
            // ... logout and me ...
            Route::post('/social/{provider}/link', 'linkProvider');
            Route::delete('/social/{provider}', 'unlinkProvider');
        });

6. Add the social actions to `AuthController` (the module keeps exactly one Controller and one Service). The response contract is the login envelope; failures follow the central exception rules:

        public function socialLogin(SocialLoginRequest $request, string $provider): JsonResponse
        {
            try {
                $code = $this->authService->socialLogin($provider, $request->validated());

7. Implement the identity resolution and linking in `AuthService`. Socialite resolves the identity only; token issuance stays on the unchanged `issueAuthorizationCode()` mechanics:

        /**
         * Resolve the provider identity and issue an authorization code
         * exactly like login() does.
         */
        public function socialLogin(string $provider, array $data): string
        {
            $identity = $this->resolveProviderIdentity($provider, $data);
            $user = $this->resolveUserForIdentity($identity);

            try {
                return $this->issueAuthorizationCode(
                    $user,
                    $data['client_id'],
                    $data['redirect_uri'],
                    $data['code_challenge'],
                    $data['code_challenge_method'],
                );
            } catch (OAuthServerException) {
                throw ValidationException::withMessages([
                    'client_id' => 'The provided client or redirect URI is invalid.',
                ]);
            }
        }

        /**
         * Verify the provider credential with the correct method and return
         * the identity. Providers outside the allowlist answer 404 through
         * the central handler before any provider interaction.
         */
        protected function resolveProviderIdentity(string $provider, array $data): array
        {
            if (! in_array($provider, config('social.enabled_providers'), true)) {
                abort(404);
            }

            if (! empty($data['id_token'])) {
                return $this->identityFromIdToken($provider, $data['id_token']);
            }

            $socialUser = Socialite::driver($provider)->userFromToken($data['access_token']);

            return [
                'provider' => $provider,
                'provider_user_id' => (string) $socialUser->getId(),
                'name' => (string) $socialUser->getName(),
                'email' => (string) $socialUser->getEmail(),
                'email_verified' => (bool) ($socialUser->user['email_verified'] ?? false),
            ];
        }

        /**
         * ID tokens are verified with the provider's own verification path —
         * signature (JWKS), issuer, audience, expiry — never decoded
         * unverified. Google example through google/apiclient.
         */
        protected function identityFromIdToken(string $provider, string $idToken): array
        {
            $payload = (new \Google\Client(['client_id' => config('services.google.client_id')]))
                ->verifyIdToken($idToken);

            if (! $payload) {
                throw ValidationException::withMessages([
                    'id_token' => 'The provider token is invalid.',
                ]);
            }

            return [
                'provider' => $provider,
                'provider_user_id' => (string) $payload['sub'],
                'name' => (string) ($payload['name'] ?? ''),
                'email' => (string) ($payload['email'] ?? ''),
                'email_verified' => (bool) ($payload['email_verified'] ?? false),
            ];
        }

        /**
         * Match on (provider, provider_user_id) only; auto-link on email
         * only when the provider confirms the email is verified.
         */
        protected function resolveUserForIdentity(array $identity): User
        {
            $socialAccount = SocialAccount::where('provider', $identity['provider'])
                ->where('provider_user_id', $identity['provider_user_id'])
                ->first();

            if ($socialAccount) {
                return $socialAccount->user;
            }

            $existingUser = User::where('email', $identity['email'])->first();

            if ($existingUser && ! $identity['email_verified']) {
                throw ValidationException::withMessages([
                    'email' => 'This email is already registered. Log in with your password and link the account from your profile.',
                ]);
            }

            return DB::transaction(function () use ($identity, $existingUser): User {
                $user = $existingUser ?? User::create([
                    'name' => $identity['name'],
                    'email' => $identity['email'],
                    'password' => null,
                    'email_verified_at' => $identity['email_verified'] ? now() : null,
                ]);

                if (! $existingUser) {
                    $user->assignRole(config('social.default_role'));
                }

                SocialAccount::create([
                    'user_id' => $user->id,
                    'provider' => $identity['provider'],
                    'provider_user_id' => $identity['provider_user_id'],
                ]);

                return $user;
            });
        }

        /** Attach the resolved provider identity to the authenticated user. */
        public function linkProvider(User $user, string $provider, array $data): void
        {
            $identity = $this->resolveProviderIdentity($provider, $data);

            $taken = SocialAccount::where('provider', $identity['provider'])
                ->where('provider_user_id', $identity['provider_user_id'])
                ->first();

            if ($taken) {
                if ($taken->user_id === $user->id) {
                    return; // already linked to the caller — idempotent success
                }

                throw ValidationException::withMessages([
                    'provider' => 'This provider identity is already linked to another account.',
                ]);
            }

            DB::transaction(fn (): SocialAccount => SocialAccount::create([
                'user_id' => $user->id,
                'provider' => $identity['provider'],
                'provider_user_id' => $identity['provider_user_id'],
            ]));
        }

        /** Detach the provider identity; never leave the account without a login method. */
        public function unlinkProvider(User $user, string $provider): void
        {
            $socialAccount = SocialAccount::where('user_id', $user->id)
                ->where('provider', $provider)
                ->first();

            if (! $socialAccount) {
                abort(404);
            }

            $hasOtherIdentity = SocialAccount::where('user_id', $user->id)
                ->where('provider', '!=', $provider)
                ->exists();

            if (is_null($user->password) && ! $hasOtherIdentity) {
                throw ValidationException::withMessages([
                    'provider' => 'You cannot unlink your last login method.',
                ]);
            }

            DB::transaction(fn () => $socialAccount->delete());
        }

## Passport 13 Setup Sequence

Laravel Passport 13 publishes its migrations instead of loading them automatically, and `passport:install` re-runs migrations internally. Never run `passport:install` on a database that already contains the oauth tables; it fails with "table already exists".

Run the following commands in this exact order:

1. `php artisan vendor:publish --tag=passport-migrations` — Passport 13 does not auto-load its migrations.
2. `php artisan vendor:publish --tag=telescope-migrations` — then delete any duplicated `*_create_oauth_*` migration files this publish may re-copy (keep exactly one migration per oauth table; the earliest timestamp).
3. `php artisan migrate`
4. `php artisan passport:keys`
5. `php artisan db:seed` — after the project's seeders (Roles and Permissions Seeder and `PassportClientSeeder`) are registered in `DatabaseSeeder`.

The OAuth clients are created by seeding, not by artisan commands:

- The approved `PassportClientSeeder` template (`templates/database/seeders/PassportClientSeeder.php`) is copied into the project by the scaffold and must be registered in `DatabaseSeeder` together with the other project seeders.
- It is the single authoritative creator of both OAuth clients in every database (main and test): because it runs with every `db:seed`, and the test suite re-seeds on every refresh (`tests/TestCase.php` with `RefreshDatabase` and `public $seed = true`), login-dependent tests always find both clients. Do not run `passport:client` commands in project setup — bypassing the seeder hides a broken client definition until the isolated test database exposes it.
- The seeder creates:
  - **Personal Access Client** — `grant_types: ["personal_access"]`; keeps `User::createToken()` working for non-lifecycle uses.
  - **First Party PKCE Client** — `grant_types: ["authorization_code", "refresh_token"]`, `secret: null` (public client), `redirect_uris: [config('app.url')]`; this is the client the login flow validates and the token endpoint exchanges codes and refresh tokens for, and the client whose id, first registered redirect URI, and S256 method the generated documentation file and the public documentation endpoint expose in their leading Public Authentication Configuration section.
- Passport 13 `oauth_clients` column contract: client ids are UUIDs, `redirect_uris` and `grant_types` are JSON-cast arrays, `secret` is nullable (null means a public client), `provider` is nullable, and `revoked` is required. The old `redirect` and `public` columns no longer exist; a seeder that writes them fails with "Unknown column".

Additional rules:

- `scripts/scaffold.sh` implements this sequence automatically (migrations, keys, conditional seeding).
- The authentication identity is the single `App\Models\V1\User` model: the scaffold installs it from the approved template (UUID hook, Passport `HasApiTokens`, Spatie `HasRoles`), removes the skeleton's default `app/Models/User.php` and `database/factories/UserFactory.php`, and installs `config/auth.php` from the approved template so the users provider resolves `App\Models\V1\User`. The Passport `api` guard, Spatie's user resolution, seeders, and factories must all resolve users through that provider — never create or reference `App\Models\User`.
- When publishing package configs, verify the actual publish tag against the package provider. Known mismatch: `l5-swagger` has no `l5-swagger-config` tag — copy `vendor/darkaonline/l5-swagger/config/l5-swagger.php` to `config/l5-swagger.php` directly.
- On Laravel 13 the skeleton has no `app/Http/Middleware/` directory; create it before copying the approved `SetLocale` template.

## Authentication Route Middleware

Authentication middleware is applied at the route level, never inside Controller constructors:

- Every protected module route file applies the `api` guard on its route group: `Route::middleware('auth:api')->controller({{Module}}Controller::class)->prefix('{{module}}')->group(...)`. Never apply `$this->middleware('auth:api')` in any Controller constructor (including `AuthController`).
- Authentication-only endpoints (`register`, `login`, `logout`, `me`, and the password reset / email verification lifecycle endpoints) are gated by Passport authentication middleware, not by permission middleware. In the Auth module route file (installed by the scaffold from `templates/routes/v1/auth.php`), `register`, `login`, `forgot-password`, `reset-password`, and the signed `email/verify/{uuid}/{hash}` route stay public (each guarded by its approved rate limiter or signature check, see Rate limiting above), and `logout`, `me`, and `email/resend` are registered inside an `auth:api` middleware group:

        Route::controller(AuthController::class)
            ->prefix('auth')
            ->group(function () {
                Route::post('/register', 'register')->middleware('throttle:auth');
                Route::post('/login', 'login')->middleware('throttle:auth');
                Route::post('/forgot-password', 'forgotPassword')->middleware('throttle:password_reset');
                Route::post('/reset-password', 'resetPassword')->middleware('throttle:password_reset');
                Route::get('/email/verify/{uuid}/{hash}', 'verifyEmail')
                    ->middleware('signed')
                    ->name('verification.verify'); // public: the signature is the authorization

                Route::middleware('auth:api')->group(function () {
                    Route::post('/logout', 'logout');
                    Route::get('/me', 'me');
                    Route::post('/email/resend', 'resendVerificationEmail')->middleware('throttle:email_resend');
                });
            });

- `logout` and `me` MUST reject unauthenticated requests with `401` — rendered by the central exception handler — before the controller action runs. Without the route-level `auth:api` middleware, `auth()->user()` returns `null` inside the action and the endpoint fails with `500` instead of `401`.
- Do not attach `permission:` middleware to authentication-only endpoints: any authenticated user may log out or retrieve their own profile. Permission middleware stays per-action in the Controllers of the business modules (see the Mandatory Authorization rules).
- `POST /oauth/token` — registered by the application in `AppServiceProvider` (see Passport route hardening under Token Lifecycle) — is the only OAuth route; it sits outside the `api/v1` prefix and every other Passport route answers `404`. Do not re-enable Passport's automatic routes, redefine, rename, or move this endpoint.
