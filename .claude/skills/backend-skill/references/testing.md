# Testing Standards

## 1. Testing Framework

- Use **PHPUnit** as the mandatory testing framework.
- Do not use Pest.
- Use Laravel's built-in testing tools and conventions.
- Feature Tests are the primary testing approach.
- Unit Tests are optional and should be added only when the business logic justifies them.

## 2. Testing Execution Timing

Testing must be performed **after the entire project has been created**, not after each module.

Follow this sequence:

1. Complete the implementation of all requested modules and features.
2. Review the implemented business logic and identify important rules and complex logic.
3. Create Feature Tests for the required modules and critical workflows.
4. Identify business logic that requires isolated Unit Tests and create them.
5. Run the complete test suite together.
6. Fix failures and rerun the tests until all tests pass.
7. Perform the final project verification.

Do not run the complete testing process after every individual module.

## 3. Test Directory Structure

Organize tests by API version, matching the project's architecture.

```text
tests/
├── Feature/
│   └── V1/
│       ├── CategoryTest.php
│       ├── BookTest.php
│       └── BorrowingTest.php
└── Unit/
    └── V1/
        └── PricingTest.php
```

- Feature Tests must be placed directly under `tests/Feature/V1/`.
- Unit Tests must be placed directly under `tests/Unit/V1/`.
- Do not create module-specific subdirectories inside the test directories.
- Use descriptive test class and method names.

## 4. Test Environment Setup

Before writing or running any tests, prepare the isolated testing environment.

### 4.1 phpunit.xml Is the Source of Truth

Laravel's default `phpunit.xml` ships with SQLite:

```xml
<env name="DB_CONNECTION" value="sqlite"/>
<env name="DB_DATABASE" value=":memory:"/>
```

These two lines **MUST** be replaced with the isolated MySQL test database:

```xml
<env name="DB_CONNECTION" value="mysql"/>
<env name="DB_DATABASE" value="project_name_test"/>
```

- The test database name follows the project's naming conventions: the main database name in lowercase snake_case with a `_test` suffix (for example `project_name` and `project_name_test`).
- Do not leave the `sqlite` / `:memory:` defaults in place. Tests would silently run against SQLite, which does not enforce foreign keys and cascades the same way as MySQL and would hide migration and cascade bugs. SQLite is forbidden in this project's standards.
- `phpunit.xml` `<php>` values override both `.env` and `.env.testing` during `php artisan test` and `vendor/bin/phpunit`. Configure the test database and the following drivers here (these are present in Laravel's default file; keep them):
  - `SESSION_DRIVER=array`
  - `CACHE_STORE=array`
  - `MAIL_MAILER=array`
  - `QUEUE_CONNECTION=sync`
  - `BROADCAST_CONNECTION=null`
  - `BCRYPT_ROUNDS=4`
- Do not rely on the presence of `.env.testing` as proof of the correct test database (see §8.2). `phpunit.xml` is authoritative for the testing environment.
- `CACHE_STORE=array` also isolates the rate limiters: rate-limit counters live in the cache, and the array store is rebuilt for every test, so throttled requests in one test never leak into another (the scaffold-installed `AuthTest.php` relies on this).

### 4.2 Create the Test Database

- MySQL does not create the database automatically, unlike SQLite `:memory:`. Before the first test run, create the isolated test database if it does not exist (for example `CREATE DATABASE IF NOT EXISTS project_name_test`).
- The test database is disposable and fully managed by the test suite (migrations, refresh, seeding, cleanup).
- Never point any testing configuration at the main development or production database.

### 4.3 Pre-Flight Checks Before the First Run (Mandatory)

Before running the complete test suite for the first time, run the following checks in order. They exist to surface bootstrap-level problems (missing autoloaded classes, absent tables, broken seeders) in seconds instead of burning a full-suite run on them:

- Verify `APP_KEY` is available in the testing environment (loaded from `.env.testing` when present, otherwise from `.env`).
- Verify the Passport key pair exists (`storage/oauth-private.key` / `storage/oauth-public.key`, generated by `passport:keys` during project setup). Tests reuse these keys; no separate test keys are required.
- Verify the project uses the approved base `tests/TestCase.php` (scaffold-installed): it must `use RefreshDatabase` and set `public $seed = true`. Without the trait, no migration or seeding happens and every database-dependent test fails with "table not found".
- **Smoke run (mandatory):** execute exactly one real authentication feature test through PHPUnit, for example `php artisan test --filter=AuthTest::test_login_issues_an_authorization_code`. This single run boots the app with `phpunit.xml` (so the isolated test database is guaranteed — see §4.1), runs `RefreshDatabase` (fresh migrations), executes `DatabaseSeeder` (roles, permissions, admin user, and both OAuth clients), autoloads all factories, and exercises the complete login flow. It must pass before the full suite is attempted.
- If the smoke run fails at bootstrap (unknown classes, missing tables, seeder SQL errors), fix the root cause in the project and re-run the smoke test — do not iterate on the full suite for bootstrap failures (§14).
- Do not replace the smoke run with manual `php artisan migrate` / `db:seed` calls against the test database: without a `.env.testing` file those commands fall back to `.env` and would target the main database (§8.2). The PHPUnit smoke run is authoritative because `phpunit.xml` always wins inside the suite.

## 5. Feature Tests

Feature Tests are the foundation of the project's testing strategy.

They must test application behavior through Laravel's HTTP testing tools, covering the complete request lifecycle without requiring a running web server or browser.

Test the important scenarios for each module based on its actual requirements.

### 5.1 HTTP Testing Requirements

- All Feature Tests MUST use Laravel's JSON testing methods: `getJson()`, `postJson()`, `putJson()`, `deleteJson()`.
- These methods send `Accept: application/json`, which is required so centralized exception and validation handling returns the approved JSON envelope. Plain `get()` / `post()` calls may receive HTML error pages instead, silently hiding violations of the "never return alternative JSON response structures" rule in `references/api-standards.md`.
- Assert the approved response envelope on every response:
  - The `message`, `status_code`, and `data` keys exist.
  - `status_code` equals the actual HTTP status code.
  - List responses nest Laravel's paginator structure inside `data`: the keys `data`, `links`, and `meta`.
- Assert that success messages follow the dynamic message convention in `references/api-standards.md` (for example `Categories created successfully.`), never generic messages.

### 5.2 CRUD Coverage

For modules that implement CRUD operations, cover the relevant scenarios:

**Create**
- Successful creation.
- Validation failures.
- Duplicate data prevention when required by business rules.
- Immutable fields (`id`, `uuid`) sent in the request payload must be ignored and must not alter the created record (mass assignment protection; they are excluded from `$fillable`).

**List**
- Correct returned records.
- Pagination behavior: `per_page` is respected.
- Sorting behavior: `sortBy` and `sortDirection` produce the expected order.
- Invalid `sortBy` (not in the approved whitelist) and invalid `sortDirection` never cause a 500 error or an SQL error; the approved fallback or validation behavior applies.
- A page beyond the last page returns an empty nested `data` array with valid `links` and `meta`.
- An empty table returns an empty data set with a valid response structure.

**Show**
- Successful retrieval using UUID.
- Nonexistent or malformed UUID handling returns the approved not-found response, never a 500 error.
- The response exposes `uuid` and never exposes the database `id`.

**Update**
- Successful update.
- Validation failures.
- Nonexistent UUID handling.
- Immutable fields (`id`, `uuid`) sent in the request payload are ignored.

**Delete**
- Successful deletion, verified with `assertDatabaseMissing` (records are truly removed; SoftDeletes is forbidden).
- Nonexistent UUID handling.

**Bulk Delete**
- Successful deletion of all requested records.
- Failure when one or more UUIDs do not exist.
- Verify all-or-nothing behavior: no records should be deleted if any requested UUID is invalid (`assertDatabaseCount` is unchanged).

**Cascade and Relationship Behavior**
- Verify Eloquent relationships load correctly (hasMany, belongsTo, belongsToMany).
- When deleting a parent record is a supported operation, verify the approved `ON DELETE CASCADE` behavior: dependent rows are removed and no orphaned foreign keys remain.
- When business rules block deleting a referenced record, verify the operation fails with the approved response and no data changes.

**Database State Assertions**
- Every write test must verify the actual database state (`assertDatabaseHas`, `assertDatabaseMissing`, `assertDatabaseCount`), not only the HTTP response.

Do not create unnecessary or repetitive tests. Focus on meaningful scenarios and actual business requirements.

### 5.3 Business Rules

Test important business rules through Feature Tests when they affect the application's actual behavior.

Examples:

- A student can borrow an available book.
- A student cannot borrow an unavailable book.
- Available copies decrease after a successful borrowing.
- Available copies increase after returning a book.
- A borrowing cannot be returned twice.
- A user cannot return another user's borrowing.

Business rule tests must also verify the resulting database state (quantities, counters, status changes), not only the response payload.

These are examples only. Determine the actual scenarios from the project's requirements.

### 5.4 Authentication and Authorization

When authentication and permissions are implemented, test:

- Unauthenticated requests where authentication is required.
- Authenticated access.
- Users without the required permission.
- Users with the required permission.
- Access restrictions between users when applicable.
- Rate limiting on the sensitive endpoints: exceeding the `throttle:auth` login limits returns the approved 429 envelope with the `Retry-After` header, and the per-email and per-IP buckets block independently. The scaffold-installed `AuthTest.php` rate-limiting tests are the approved pattern (references/api-standards.md, Rate Limiting); the scaffold-installed `PasswordResetTest.php` and `EmailVerificationTest.php` extend the pattern to the `throttle:password_reset` and `throttle:email_resend` limiters.

Follow §9 for the approved Passport authentication mechanics in tests.

### 5.5 Validation and Error Handling

Verify that:

- Invalid input is rejected.
- Required business validations are enforced.
- Error responses follow the project's standard API response structure.
- Failed operations do not leave partial database changes.
- Transaction-based operations preserve data consistency.

Assert the approved status codes for every scenario:

| Scenario | Status |
|---|---|
| Successful operation (including Create) | 200 |
| Validation failure | 422 |
| Unauthenticated request | 401 |
| Missing permission | 403 |
| Nonexistent or malformed UUID / record | 404 |
| Rate limit exceeded | 429 (with `Retry-After`) |

All success operations use the `apiResponse()` default of 200. Assert both the HTTP status and the `status_code` envelope field.

## 6. Unit Tests

Unit Tests are optional and must be created selectively.

The AI must review the implemented Business Logic after completing the project and decide which parts genuinely require isolated testing.

### 6.1 When to Create Unit Tests

Create Unit Tests when the implementation contains important or sufficiently complex logic, such as:

- Complex calculations involving multiple conditions.
- Business rules that depend on several related factors.
- Decision-making logic with multiple possible outcomes.
- Complex eligibility or availability checks.
- Pricing, discounts, fees, or other calculation rules.
- Logic whose correctness is important and would benefit from independent testing.

Do not create Unit Tests for every function, method, or Service method.

Simple CRUD operations and straightforward database queries do not automatically require Unit Tests. Their important behavior should normally be covered by Feature Tests.

### 6.2 How to Decide What to Test

The AI must evaluate the actual business requirements and implementation rather than following a fixed number of Unit Tests per module.

For example, in a Booking module:

- Feature Tests verify the actual booking API workflow.
- Unit Tests can independently verify complex pricing calculations, discount rules, availability decisions, and other isolated business logic.

When a business operation coordinates multiple functions or collaborators, a Unit Test may verify their combined business behavior when the relevant dependencies can be isolated or mocked.

If correctness depends on actual database interactions, Eloquent relationships, transactions, or the complete Laravel application flow, prefer a Feature Test rather than forcing the scenario into a Unit Test.

### 6.3 Unit Testing Rules

- Test meaningful business behavior, not merely method execution.
- Cover important expected outcomes and relevant failure conditions.
- Use mocks or fakes when appropriate to isolate dependencies.
- Avoid unnecessary tests for simple getters, setters, or trivial methods.
- Do not duplicate Feature Test coverage without a clear reason.
- Do not create Unit Tests just to increase test count.

## 7. Test Data: Factories and Seeders

- Use Laravel Model Factories as the primary method for generating test data.
- Use existing factories whenever possible.
- Create or update factories when the actual project models require them.
- Use Seeders when predefined base data is necessary, such as Roles, Permissions, or other required reference data.
- Run any required seeders only against the isolated Test Database.
- Do not depend on manually inserted production or development data.
- Each test must prepare the data it needs and must not depend on another test's execution order.

### 7.1 Seeder Strategy in Tests

- Feature Tests use Laravel's `RefreshDatabase` trait.
- Enable seeding by setting `public $seed = true` on the base `TestCase`, so `DatabaseSeeder` runs against the isolated test database when the suite is refreshed.
- `DatabaseSeeder` must register the Roles and Permissions Seeder, as required by the approved project setup, so roles and permissions exist in every test.
- Additional module reference data comes from module seeders registered in `DatabaseSeeder`; per-test records come from factories.
- Never run development seeders against the main database to prepare tests, and never depend on the main database's data inside tests.

## 8. Test Database Isolation and Safety

Testing must use a separate database that is completely isolated from the project's main database.

For example:

```text
project_name
project_name_test
```

The actual test database name can follow the project's naming conventions and is configured in `phpunit.xml` (see §4.1).

### 8.1 Database Rules

- Configure a dedicated testing database.
- Use the testing environment configuration appropriately.
- Verify the actual active database connection before executing destructive operations.
- Never run testing operations against the main development or production database.
- Never delete or modify existing main database data during testing.

### 8.2 Testing Database Operations

The AI may freely perform testing-related operations against the isolated Test Database, including:

- Running migrations.
- Refreshing the testing database.
- Using `RefreshDatabase` where appropriate.
- Running testing seeders.
- Creating and deleting test records.
- Cleaning up test data.

Before using destructive commands such as `migrate:fresh`, verify that the active connection points to the isolated Test Database.

Do not rely solely on the presence of `.env.testing` as proof that the correct database is active. The `phpunit.xml` database values are authoritative for the test suite; when running an Artisan command manually against the test database, use `--env=testing` and verify the target database name in the command output.

### 8.3 Database-Related Project Fixes

If testing reveals an actual problem in a project migration, model, factory, relationship, or other project file, fix the actual project implementation when necessary.

However, all testing database operations must remain isolated from the main project database.

## 9. Passport Authentication in Tests

Protected endpoints must be tested with real Passport tokens, following the project's actual authentication flow (references/authentication.md, Token Lifecycle):

- Authenticate by running the complete login flow with the credentials of a user created by the test seeders or factories:
  1. `POST /api/v1/auth/login` with `email`, `password`, the seeded First Party PKCE Client `client_id`, `redirect_uri`, and a generated PKCE `code_challenge`/`code_challenge_method=S256` — returns the authorization code in `data.code`.
  2. `POST /oauth/token` with `grant_type=authorization_code`, the `code`, and the matching `code_verifier` — returns `{token_type, expires_in, access_token, refresh_token}`.
- Attach the returned access token to subsequent requests with `withToken($accessToken)` or the `Authorization: Bearer` header.
- Do not use database IDs, mock identities, or fabricated token strings in place of the real login flow. Do not authenticate tests with `User::createToken()`; it bypasses the lifecycle under test.

The scaffold installs `tests/Feature/V1/AuthTest.php`, the approved lifecycle feature test, in every project: it covers login issuing an authorization code, the code exchange issuing both tokens, refresh rotation (old access token and old refresh token revoked in the database), reuse of a consumed refresh token, invalid and unknown-client refresh tokens, access-token and refresh-token expiry, logout revoking both tokens, 401/422 behavior, the Passport route hardening contract (`POST /oauth/token` as the only registered OAuth route — the endpoint rejects other methods with 405, keeps the `throttle` middleware — and every other Passport route answering 404), and the rate limiting contract (the `throttle:auth` login limits returning 429 with `Retry-After`, the independent per-email and per-IP buckets, and normalized email keys). Do not weaken or delete these tests; extend them only for additional business requirements.

The scaffold also installs `tests/Feature/V1/DocumentationTest.php`, the public documentation endpoint spec: public accessibility (`text/markdown` without authentication), the response beginning with the Public Authentication Configuration section resolving the seeded First Party PKCE Client's `client_id` and first registered `redirect_uri` dynamically at request time with `code_challenge_method` `S256` (a re-seeded client is reflected without regenerating the file), no client secret or personal-access client id anywhere in the response, the stale generation-time section stripped when the client is missing, and the unchanged file-serving and 404 behaviors. Do not weaken or delete these tests.

The scaffold also installs `tests/Feature/V1/PasswordResetTest.php`, the native password reset spec (references/authentication.md, Password Reset): the neutral 200 link answer for registered and unknown addresses (`assertNothingSent()` for unknown emails), email validation (422), the native broker throttle answering 429 with `Retry-After`, the route-level `throttle:password_reset` per-IP bucket, the password actually changing (Hash checks on old and new values, `remember_token` rotation), the single-use token (row deleted from `password_reset_tokens`, replay answered 422), invalid token, unknown email, and password rule failures (422 with the token still usable), and login succeeding with the new password while the old one fails. Emails are intercepted with `Notification::fake()` and the reset token is read from the faked `ResetPassword` notification — the suite never sends real mail and never queries the raw token hash. Do not weaken or delete these tests.

The scaffold also installs `tests/Feature/V1/RegisterTest.php`, the registration spec (references/authentication.md, Registration): the 201 success with the user row actually created (uuid from the model hook, `Hash::check` on the stored password, `email_verified_at` still null), the response payload carrying the uuid and never the database id, the native `VerifyEmail` notification sent automatically (`Notification::assertSentTo`), the emailed link's action URL addressing the user by uuid and never by the database id, login succeeding through the unchanged PKCE flow before verification, and the duplicate email / invalid email / short password / unconfirmed password / missing name failures answering 422 with nothing sent (`Notification::assertNothingSent()`). Emails are intercepted with `Notification::fake()` — the suite never sends real mail. Do not weaken or delete these tests.

The scaffold also installs `tests/Feature/V1/EmailVerificationTest.php`, the native email verification spec (references/authentication.md, Email Verification): the signed link verifying the email (`markEmailAsVerified` stamping `email_verified_at`), idempotent re-following, expired and tampered links rejected with 403 before the controller runs, a signature-valid link with a wrong hash rejected with 422, an unknown uuid answered 404, the authenticated resend sending the native `VerifyEmail` notification (`Notification::assertSentTo`), the already-verified resend rejected with 422, and the unauthenticated resend answered 401. The signed URLs are built with `URL::temporarySignedRoute('verification.verify', ..., ['uuid' => $user->uuid, ...])` — exactly the way the framework's notification builds them through the `VerifyEmail::createUrlUsing()` hook in the `AppServiceProvider` — and every authenticated request runs the real authorization code + PKCE login flow (§9 above). Do not weaken or delete these tests.

**OAuth clients in the test database:**

- The login flow resolves the public First Party PKCE Client from the `oauth_clients` table; the PKCE pair in tests is generated the same way frontends generate it (`rtrim(strtr(base64_encode(random_bytes(48)), '+/', '-_'), '=')` for the verifier, `base64url(sha256(verifier))` for the challenge).
- Both clients are created by the project's `PassportClientSeeder` (registered in `DatabaseSeeder` per `references/authentication.md`), so every database — main and test — receives them through seeding: the test database on every suite refresh via `public $seed = true` on the base `TestCase`.
- The First Party PKCE Client must satisfy the contract: `revoked = false`, `secret = null` (public client), `provider` null (or matching `auth.guards.api.provider`), and `grant_types` containing `authorization_code` and `refresh_token`. Without a valid client row, every login-dependent test fails.

Authentication tests must also verify:

- Wrong credentials return the approved validation response (422).
- Requests without a token return 401.
- Logout revokes the access token AND its associated refresh token, the next request with the same access token returns 401, and the refresh token can no longer be used at `/oauth/token`.

**Token guard caching between in-process requests:**

- Passport's token guard caches the resolved user for the lifetime of the PHP process. In a feature test, several requests share one process, so a request that follows a logout still resolves the cached user and would pass with a revoked token — the revocation is never re-validated.
- After a logout (or any token revocation), reset the resolved guards before the next request so it re-validates the token against the database exactly as a fresh production request would:

```php
$this->app['auth']->forgetGuards();

$this->getJson('/api/v1/auth/me', ['Authorization' => 'Bearer '.$token])
    ->assertStatus(401);
```

Passport key files are shared between environments; tests require no separate keys.

## 10. Time-Dependent Logic

- Freeze time with `Carbon::setTestNow()` when testing time-sensitive behavior, such as OTP expiry, loan or booking periods, availability windows, and subscription states.
- Advance time deliberately (for example by moving the frozen time forward) to test expiry and boundary conditions.
- Reset the frozen time in the test's cleanup (`tearDown`) so it never leaks into other tests.
- Do not write tests that depend on real wall-clock timing, `sleep()`, or execution speed; such tests are flaky.

**OAuth token expiry — the one sanctioned exception:**

- Passport/league validate OAuth token expiry against the real system clock (`time()` inside league; the JWT `exp` claim and the encrypted refresh token payload carry no injectable clock), and the database `expires_at` columns are not consulted by the token guard. `Carbon::setTestNow()` and `travel()` therefore do NOT expire an OAuth access or refresh token.
- The approved pattern (implemented in the scaffold-installed `AuthTest.php`) is: override the TTL for that test only — `Passport::tokensExpireIn(now()->addSeconds(1))` or `Passport::refreshTokensExpireIn(now()->addSeconds(1))` — run the login flow, then `sleep(2)` before asserting the 401 / `invalid_grant` behavior. Restore the production TTLs from `config/oauth.php` in `tearDown`, because Passport TTL setters write static state that would otherwise leak into other tests.
- This is the only sanctioned `sleep()` in the test suite. Keep the 1-second TTL and the 2-second sleep pair intact: the margin is what makes the test deterministic.

## 11. External Services

- Tests must never call real third-party providers: Twilio OTP, Social Login (Socialite) providers, S3 or other external storage, payment, notification, or messaging providers.
- Mock the service class, or use Laravel's fakes: `Http::fake()` for outbound HTTP, `Storage::fake()` for storage disks, `Mail::fake()`, `Notification::fake()`, and `Queue::fake()` where applicable.
- Tests must pass without real provider credentials and without network access to external services.
- A test must never fail or pass based on an external provider's availability or rate limits.

## 12. File Storage Testing

Follow `references/file-storage.md` and verify file behavior with `Storage::fake()` on the disk used by the feature:

**Upload**
- A successful upload stores the file at the path recorded in the database: assert both `Storage` contains the file and the database record references the exact returned path.
- Invalid uploads (wrong type, too large) are rejected with 422 and no file is stored.
- Two uploads with the same original filename produce two distinct stored files; the second never overwrites the first.

**Replacement**
- The new file exists and the database references the new path.
- The old file is kept until the database transaction succeeds; if the operation fails, the old file remains and the database still references it (no partial replacement).
- No orphaned new file remains after a failed operation when safe cleanup applies.

**Deletion**
- Deleting a record that references a file removes the file only after the database deletion succeeds.
- If the delete operation fails, both the record and the file remain unchanged.

Never assert or rely on filesystem operations rolling back with a database transaction; the filesystem does not participate in database transactions.

## 13. Localization Testing

- The default project has no `lang` directory: Feature Tests assert the English literal messages directly (the scaffold-installed Auth module tests show the approved pattern), and no test may depend on `__('messages.*')` keys.
- Include at least one test verifying the approved `SetLocale` middleware behavior in the default project:
  - The application locale stays `en` for any `Accept-Language` header — supported, unsupported, or missing — because the middleware's supported-language list contains only `['en']`.
- When the project explicitly requested additional languages, verify the generated localization:
  - For every requested locale, `Accept-Language: {locale}` produces that language's behavior or translated content.
  - An unsupported or missing header falls back to `en`.
- When the project uses translated validation or business messages, verify that error messages respect the requested locale.

## 14. Failure Handling and Test Repair

Passing tests is mandatory. The AI must not hide or ignore test failures.

Whenever a test fails:

1. Read the complete failure message and relevant stack trace.
2. Identify the actual root cause.
3. Determine whether the problem is in the project implementation, the test itself, or the testing environment.
4. Fix the actual problem.
5. Rerun the failed test.
6. Rerun related tests to ensure the fix did not introduce regressions.
7. Rerun the complete test suite.
8. Repeat this process until all tests pass.

While repairing a failure, re-run only the failing test to keep the loop fast:

```bash
php artisan test --filter=CategoryTest::test_method_name
```

After fixing, re-run the related tests and then the complete suite.

Do not run the suite with `--parallel`. Tests share one MySQL test database; parallel processes conflict with each other and with the shared schema. Keep test runs sequential.

### Important Restrictions

Never:

- Skip a failing test to make the suite pass.
- Disable or delete a test simply because it fails.
- Weaken assertions to hide an implementation problem.
- Change business requirements just to satisfy an incorrect implementation.
- Ignore transaction, validation, or authorization failures.
- Claim that testing is complete while known test failures remain unresolved.

If a test itself is incorrect or contradicts the actual business requirements, correct the test while preserving the intended requirement.

If the failure is caused by dependencies, configuration, database setup, or the testing environment, fix the root cause when possible.

If a genuine blocker cannot be resolved, clearly report it and explain why the test could not be completed. Never report an unsuccessful test suite as successful.

## 15. Final Verification

After all Feature Tests and Unit Tests have been created, run the complete suite:

```bash
php artisan test
```

After successful testing, perform the following verification:

```bash
php artisan route:list
php artisan migrate:status
```

Note: `php artisan test` uses the `phpunit.xml` database overrides, but plain Artisan commands such as `migrate:status` run against the active environment's database. Verify the main database with the normal environment, and use `--env=testing` when inspecting the test database.

Also:

- Inspect Laravel logs for unexpected Exceptions or Errors.
- Verify that the required routes are registered.
- Verify that migrations have been executed successfully.
- Verify that no known test failures remain.
- Fix any discovered problems and repeat the relevant tests and verification.

## 16. Completion Requirements

The testing phase is complete only when:

- Required Feature Tests have been created.
- Necessary Unit Tests have been identified and created.
- All tests pass successfully.
- `phpunit.xml` points to the isolated MySQL test database, with no `sqlite` / `:memory:` defaults remaining.
- The Test Database remains isolated from the main database.
- Final verification commands complete successfully.
- No known unresolved testing or implementation failures remain.
- The Project Completion Gate (`scripts/completion-gate.sh`) passes its test-suite criterion: the gate re-runs the complete suite (`php artisan test`) as gate criterion 6, and the project is not `READY` until it passes.

The AI must provide a concise testing summary containing:

- Total tests executed.
- Number of passed and failed tests.
- Feature Tests coverage by module.
- Unit Tests created and the business logic they cover.
- Any unresolved blockers, if applicable.

Never claim that the project is fully verified if any required testing or verification step remains incomplete.
